[Heading 2] Operating Environment
[InfoBlue] Describe the environment in which the software will operate, which might include the hardware platform; operating systems and versions; geographical locations of users, servers, and databases; and organizations that host the related databases, servers, and websites. 
[InfoBlue] Example:
[Normal] 
[InfoBlue] OE-1: The System shall operate correctly with the following web browsers: Windows Internet Explorer versions 7, 8, and 9; Firefox versions 12 through 26; Google Chrome (all versions); and Apple Safari versions 4.0 through 8.0.
[Heading 2] Design and Implementation Constraints
[InfoBlue] There are times when a certain programming language must be used, a code library that has already had time invested to develop it needs to be used, and so forth. Describe any factors that will restrict the options available to the developers and the rationale for each constraint. Constraints are described further in Chapter 14, “Beyond functionality.” 
[InfoBlue] Example:
[Normal] 
[Normal] CON-1: The system shall use the current corporate standard Oracle database engine
[Normal] CON-2: The application must use Microsoft .NET framework 4.5. 
[Normal] CON-3: Online payments may be made only through PayPal. 
[Normal] CON-3: All textual data used by the application shall be stored in the form of XML files.

[Heading 3] Requirement Identifying Technique
[InfoBlue] This section describes the technique used to identify and document the functional requirements of the system.
[Normal (Web)] For this project, Mockup-Based Requirement Analysis is used. In this approach, user interface mockups are created using UI/UX tools such as Figma, Adobe XD, or Balsamiq. These mockups visually represent how users will interact with the system. Functional requirements are then derived from each screen’s elements and behaviors.
[Heading 4] Steps to Follow:
[Normal (Web)] Identify key features and break them down into individual screens.
[Normal (Web)] Assign a Mockup ID to each screen (e.g., M1 for Login Page, M2 for Dashboard).
[Normal (Web)] Create mockups of the screens using any UI/UX design tool.
[Normal (Web)] Identify interactive elements on each screen (buttons, forms, menus, etc.).
[Normal (Web)] Derive a functional requirement from each element, describing what the system should do in response.
[Normal (Web)] Organize all functional requirements using the table format provided in Section 2.2.1.
[Normal (Web)] Backend Process Requirements
[Normal (Web)] While mockups are effective for capturing frontend interactions, some system functionalities take place entirely at the backend (e.g., order processing, payment gateway callbacks, email/SMS notifications, scheduled jobs, data validation, account security, and real-time tracking in ride-hailing apps). In addition, there are systems that operate almost entirely at the backend with minimal or no user interface, such as traffic signal control systems or industrial monitoring systems.”.
[Normal (Web)] To capture these processes, the Event–Response Table technique is used.
[Normal (Web)] It is effective for modelling backend or real-time system behaviours where user interface interactions are not directly involved.
[Normal (Web)] It describes the system’s response to specific events, often including conditions under which different actions occur.
[Normal (Web)] This ensures backend workflows are captured in the requirements phase without going into design-level details.
[Normal (Web)] For detailed guidelines and examples of both Mockup-Based Requirement Analysis and Event–Response Tables, please see Appendix A.
[Heading 3] Functional Requirements
[Normal (Web)] This section describes the functional requirements of the system derived from user interactions and mockups. To ensure clarity and maintain a stable specification, each requirement should be documented at the feature level (e.g., User Sign-In, Product Checkout), with optional reference to the specific UI element(s) from which the feature is derived. Each functional requirement must include:
[Normal (Web)] A unique identifier (e.g., FR1.1, FR1.2).
[Normal (Web)] A clear and testable requirement statement written at the feature level.
[Normal (Web)] A reference to the originating mockup screen and (if needed) the UI element that demonstrates the feature.
[Normal (Web)] An optional Business Rule, if the behavior is governed by a domain-specific policy, condition, or constraint.
[Normal (Web)] Where applicable, Business Rules help clarify why a requirement must behave in a certain way and ensure that system behavior aligns with organizational rules, legal constraints, or client policies.

[Heading 2] Non-Functional Requirements
[Normal] This section specifies non-functional requirements (NFRs) other than constraints (recorded in Section 2.3) and external interface requirements (described in Section 7). Non-functional requirements define the quality attributes of the system, such as reliability, usability, performance, and security. To avoid vague statements, these requirements must be written in specific, quantitative, and verifiable terms (e.g., using percentages, thresholds, or time limits).
[Normal] 
[Normal] To learn how to write non-functional requirements in measurable ways, students should refer to Chapter 14 “Beyond Functionality”, which provides practical guidelines and examples of quality attribute requirements.
[Heading 3] Reliability 
[Header] Requirements about how often the software fails. The measurement is often expressed in MTBF (mean time between failures). The definition of failure must be clear. Also, don't confuse reliability with availability, which is quite a different kind of requirement.  Be sure to specify the consequences of software failure, how to protect from failure, a strategy for error detection, and a strategy for correction.
[Heading 3] Usability
[Header] Usability requirements deal with ease of learning, ease of use, error avoidance and recovery, the efficiency of interactions, and accessibility. The usability requirements specified here will help the user interface designer create the optimum user experience.
[Header] Example:
[Normal] 
[Header] USE-1: The COS shall allow a user to retrieve the previous meal ordered with a single interaction.
[Heading 3] Performance
[Pa1] State specific performance requirements for various system operations. If different functional requirements or features have different performance requirements, it’s appropriate to specify those performance goals right with the corresponding functional requirements, rather than collecting them in this section. 
[Normal] Example:
[Normal] 
[Normal] PER-1:	 95% of webpages generated by the COS shall download completely within 4 seconds from the time the user requests the page over a 20 Mbps or faster Internet connection.
[Heading 3] Security 
[Header] One or more requirements about protection of your system and its data. The measurement can be expressed in a variety of ways (effort, skill level, and time) to break into the system.  Do not discuss solutions (e.g. passwords) in the requirements document.
[Heading 2] External Interface Requirements
[Pa1] This section provides information to ensure that the system will communicate properly with users and with external hardware or software elements. A complex system with multiple subcomponents should create a separate interface specification or system architecture specification. The interface documentation could incorporate material from other documents by reference. For instance, it could point to a hardware device manual that lists the error codes that the device could send to the software. 
[Heading 3] User Interfaces Requirements
[Normal] Describe the logical characteristics of each user interface that the system needs. Some possible items to include are
[List Paragraph] References to GUI standards or product family style guides that are to be followed.
[List Paragraph] Standards for fonts, icons, button labels, images, color schemes, field tabbing sequences, commonly used controls, and the like.
[List Paragraph] Screen layout or resolution constraints.
[List Paragraph] Standard buttons, functions, or navigation links that will appear on every screen, such as a help button.
[List Paragraph] Shortcut keys.
[List Paragraph] Message display conventions.
[List Paragraph] Layout standards to facilitate software localization.
[List Paragraph] Accommodation for visually impaired users.
[Normal] 
Document the user interface design details, such as specific dialog box layouts, in a separate user interface specification, not in the SRS. Including screen mock-ups in the SRS to communicate another view of the requirements is helpful but making it clear that the mock-ups are not the committed screen designs. If the SRS is specifying an enhancement to an existing system, it sometimes makes sense to include screen displays exactly as they are to be implemented. The developers are already constrained by the current reality of the existing system, so it's possible to know up front just what the modified, and perhaps the new, screens should look like.  
[Heading 3] Software interfaces
[Pa1] Describe the connections between this product and other software components (identified by name and version), including other applications, databases, operating systems, tools, libraries, websites, and integrated commercial components (If any).
[Normal] Example:
[Normal] 
[Normal] SI-1: Cafeteria Inventory System
[Normal] SI-1.1:	The COS shall transmit the quantities of food items ordered to the Cafeteria Inventory System through a programmatic interface.
[Heading 3] Hardware interfaces
[Pa1] Describe the characteristics of each interface between the software components and hardware components, if any, of the system. This description might include the supported device types, the data and control interactions between the software and the hardware, and the communication protocols to be used. For more about specifying requirements for systems containing hardware, see Chapter 26, “Embedded and other real-time systems projects.”
[Heading 3] Communications interfaces
[Normal] State the requirements for any communication functions the product will use, including email, web browser, network protocols, and electronic forms.
[Normal] 
[Normal] Example:
[Normal] 
[Normal] CI-1:	The COS shall send an email or text message (based on user account settings) to the Patron to confirm acceptance of an order, price, and delivery instructions.

[Caption] Event-Response Tables
[Normal] Example System: “Buy a Product” Feature in an E-Commerce System
[Normal] To develop an Event–Response Table, it is first required to identify all possible events that may occur in the system. The following example presents an event list and event–response table for the Buy a Product feature of an E-Commerce System.
[Normal] The “Buy a Product” feature must handle various operational and exceptional events, including the following:
[List Paragraph] A user attempts to log in to the system.
[List Paragraph] The payment gateway confirms the transaction.
[List Paragraph] The warehouse updates order shipment status.
[List Paragraph] The delivery carrier reports delivery failure.
[List Paragraph] The system detects that product stock has reached zero.
[Normal] 
[Normal] Identified Events for “Buy a Product” Feature
[Normal] User Authentication Success – triggered when the authentication server confirms valid credentials.
[Normal] User Authentication Failure – triggered when the authentication server rejects credentials.
[Normal] Payment Confirmation Received – triggered when the payment gateway confirms successful transaction.
[Normal] Order Shipped – triggered when warehouse updates order status to shipped.
[Normal] Delivery Failed – triggered when shipping carrier reports unsuccessful delivery.
[Normal] Stock Depleted Notification – triggered when product inventory reaches zero.
[Normal] 
[Normal] Note for Students: When preparing an Event–Response Table, additional attributes may be included for detailed requirement analysis, such as:
[List Paragraph] Required input data elements
[List Paragraph] Preconditions
[List Paragraph] System state before the event
[List Paragraph] System state after the response
[List Paragraph] Exception handling mechanisms
[Normal] These details improve completeness, traceability, and clarity in requirement specification.
